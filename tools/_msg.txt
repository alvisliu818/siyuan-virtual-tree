feat(terminal): 真 PTY 改由独立 helper 进程承载,绕开渲染进程 Worker 限制

实机验证发现:node-pty 在思源渲染进程里必然失败。node-pty 的
lib/windowsConoutConnection.js 无条件创建 worker_threads.Worker 排空
conout socket(源码注释:否则关闭伪控制台时死锁),而 Electron 渲染进程的
V8 platform 不支持创建 Worker,实测抛:
  Failed to construct 'Worker': The V8 platform used by this instance of
  Node does not support creating Workers
症状极具误导性:require node-pty 成功、spawn 抛异常被回退逻辑吞掉,
界面只显示「管道模式」,很容易误判成代码 bug。

方案:用 ELECTRON_RUN_AS_NODE=1 把思源 exe 当纯 Node 运行时拉起
tools/pty-helper.js,该进程内 worker_threads 与 node-pty 均可用
(实测 ANSI 真彩色 + PSReadLine 语法高亮 + 中文正常)。通信走 stdio 的
按行 JSON,不占端口、不依赖 WebSocket 组件。

- 新增 tools/pty-helper.js:以纯 Node 模式承载 node-pty,实现
  create/input/resize/kill 协议;shell 解析与插件侧规则一致
  (shell 必带 -NoExit,否则执行完立即退出失去交互)
- builtin-terminal:新增 spawnHelperTerminal,优先级为
  helper > 渲染进程直连 node-pty > child_process 管道;
  保留直连分支以备将来 Electron 放开该限制
- isPtyAvailable 改为检测 helper 就位,不再误报
- index.ts:onload 早期注入插件目录(helper 与 node-pty 均在其下)
- webpack:把 pty-helper.js 与 node-pty 一并打包(按平台,已排除 *.pdb)
- 修复时序 bug:原先 isPtyAvailable() 在插件目录注入之前执行,
  且 loadNodePty 会把 null 永久缓存,导致首次检测必失败
- 新增 tools/_cdp.mjs(零依赖 CDP 探针)与 start-siyuan-debug.ps1

实机验证(测试工作空间 54110,主空间未动):
- 后端标签 PTY,进程链 渲染进程 → helper(39280) → shell(32584)
- Get-ChildItem 表格对齐输出正常,PSReadLine 语法高亮生效(管道模式没有)
- 中文输入输出正常,无乱码
